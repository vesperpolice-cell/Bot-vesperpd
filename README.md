# VES-PD Bot v2

Discord bot สำหรับกรมตำรวจ Vesper (VES-PD) — ทำงานร่วมกับ Google Sheets เป็นฐานข้อมูลหลัก

รับผิดชอบ 4 งานหลัก: **ลงทะเบียนสมาชิกใหม่**, **นับยอดเคส**, **ลงเวลาปฏิบัติหน้าที่**, และ **ส่งต่อรายงานคดี** ระหว่างห้อง

## เริ่มต้นใช้งาน

### สิ่งที่ต้องมี

| อย่าง | เวอร์ชัน / รายละเอียด |
|---|---|
| Node.js | **22 ขึ้นไป** (แนะนำ 24 — ดู `.nvmrc`) |
| Discord Bot | เปิด **Message Content Intent** + **Server Members Intent** ใน Developer Portal |
| Google Service Account | เปิด Google Sheets API แล้วแชร์ชีตทุกใบให้อีเมลของ service account เป็น **Editor** |

### ติดตั้ง

```bash
npm install
```

```bash
cp .env.example .env
```

แล้วเปิด `.env` ใส่ค่าจริง (ดู[หัวข้อถัดไป](#ตัวแปรใน-env))

### รัน

```bash
npm run dev
```

โหมด production:

```bash
npm run build && npm start
```

> บอทจะ **ตรวจ config ทั้งหมดก่อนสตาร์ท** ถ้ามีอะไรผิดจะไม่ยอมรันและบอกเป็นภาษาไทยว่าผิดตัวไหนทั้งหมดในรอบเดียว

## ตัวแปรใน .env

### จำเป็น

| ตัวแปร | รายละเอียด |
|---|---|
| `BOT_TOKEN` | Token ของบอทจาก Discord Developer Portal |
| `CLIENT_ID` | Application ID — ตัวเลขล้วน 17–20 หลัก |
| `GUILD_ID` | ID ของเซิร์ฟเวอร์ — ตัวเลขล้วน 17–20 หลัก |

### กุญแจ Google (เลือกอย่างใดอย่างหนึ่ง)

| วิธี | รายละเอียด |
|---|---|
| `GOOGLE_JSON_KEY` | **แนะนำ** — วางไฟล์ JSON ของ service account ทั้งก้อนเป็นบรรทัดเดียว ย้ายโฮสต์ง่าย ไม่ต้องอัปโหลดไฟล์แยก |
| `credentials.json` | วางไฟล์ไว้ที่ root ของโปรเจกต์ บอทจะหาให้เองถ้าไม่มี `GOOGLE_JSON_KEY` |

> ถ้า `\n` ใน `private_key` ยังเป็นตัวอักษรสองตัว (บางโฮสต์เก็บแบบนี้) บอทจะแปลงให้เองอัตโนมัติ

### ไม่ใส่ก็ได้

| ตัวแปร | ค่า default | รายละเอียด |
|---|---|---|
| `PORT` | `3000` | พอร์ตของ HTTP server (health check) ต้องอยู่ระหว่าง 1–65535 |
| `RENDER_EXTERNAL_URL` | `http://localhost:{PORT}` | URL ของบอทบนโฮสต์ ใช้ self-ping กันโฮสต์ฟรีหลับ |
| `LOG_TO_FILE` | `true` | **บนโฮสต์แนะนำ `false`** แล้วให้แพลตฟอร์มเก็บ log จาก stdout แทน |

⚠️ `.env` และ `credentials.json` อยู่ใน `.gitignore` แล้ว **ห้าม commit เด็ดขาด**

## โครงสร้างชีตที่บอทใช้

### ชีตนับยอดเคส (`SPREADSHEET_ID` / `SHEET_NAME`)

```
แถว 1–2   (ว่าง)
แถว 3     หัวตาราง
แถว 4+    ข้อมูล
```

| คอลัมน์ | หัวตาราง | เนื้อหา |
|---|---|---|
| A | ชื่อDC | ชื่อเล่นที่ตั้งไว้ในเซิร์ฟ (เช่น `00 [VES-PD] Real Yamada`) — อัปเดตตามให้อัตโนมัติ |
| B | User ID | Discord User ID — **ใช้เป็นกุญแจหลักในการค้นแถว** |
| C | Take2 | ยอดจากห้องที่ 1 |
| D | คดีปกติ | ยอดจากห้องที่ 2 |
| E | รถยอด | ยอดจากห้องที่ 3 |
| F | คุมสอบ | ยอดจากห้องที่ 4 |
| G | อุ้มเอ๋อ | ยอดจากห้องที่ 5 |

> แถวเก่าที่ยังไม่มี User ID ในคอลัมน์ B บอทจะค้นด้วยชื่อในคอลัมน์ A ให้ก่อน แล้ว**เติม User ID ลงไปอัตโนมัติ**เพื่อให้รอบถัดไปค้นแม่นขึ้น

> **ชื่อในคอลัมน์ A อัปเดตเองทุกครั้งที่คนนั้นได้ยอด** — ใครถูกนับยอดไว้ก่อนลงทะเบียน ชื่อจะถูกแก้ให้เป็นชื่อในระบบทันทีที่ได้ยอดครั้งถัดไป (กดปุ่มนับข้อความเก่าจะซ่อมให้ทั้งชีตในรอบเดียว)
> บอทเขียนทับชื่อเฉพาะชื่อเล่นที่อยู่ในรูปแบบ `รหัส [VES-PD] ชื่อ IC` เท่านั้น — คนนอกที่ตั้งชื่อเล่นอิสระ และคนที่ออกจากเซิร์ฟไปแล้ว จะคงชื่อเดิมในชีตไว้ ไม่ถูกทับด้วยชื่อบัญชี Discord

### ชีตทะเบียนกำลังพล (`REGISTRY_SHEET_NAME`)

ข้อมูลเริ่มแถว 3 — บอทอ่าน/เขียนคอลัมน์เหล่านี้:

| คอลัมน์ | เนื้อหา |
|---|---|
| B | เบอร์โทร IC |
| C | รหัสประจำตัว (ต้องเตรียมไว้ล่วงหน้า — บอทหาแถวที่มีรหัสแต่ยังไม่มีชื่อ) |
| D | ชื่อในระบบ (`รหัส + ชื่อ IC` ตัดให้ไม่เกิน 32 ตัวอักษรตามลิมิต Discord) |
| E | Discord mention (`<@userId>`) |
| H | วันที่ลงทะเบียน |
| J, K | วันที่/เวลาเข้าเวรล่าสุด |
| M | ID จากรายงานลงเวลา |
| N | สถานะ — เขียน `ออกจาก Discord` อัตโนมัติเมื่อสมาชิกออกจากเซิร์ฟเวอร์ |
| O–U | ยอดเวลาสะสม (รูปแบบ `HH:mm`) |
| X, Y | ชื่อ/ID สำรอง |

### ชีตคิวรออนุมัติ (`PENDING_SHEET_NAME`)

| คอลัมน์ | เนื้อหา |
|---|---|
| B | Discord ID |
| D | ชื่อ IC |
| E | เบอร์ IC |
| F | อายุ OOC |
| H | สถานะ — ใส่ `อนุมัติ` เพื่อให้คนนั้นข้ามขั้นตอนกรอกฟอร์มได้เลย |

## ฟีเจอร์

### 📊 นับยอดเคส (`count`)

นับอัตโนมัติจากการแท็กในห้องที่ตั้งไว้ 5 ห้อง

- มีคนโพสต์แท็ก → กด ✅ ให้โพสต์ แล้ว **+1** ให้ทุกคนที่ถูกแท็ก
- ลบโพสต์ → **−1** คืนให้ทุกคนในโพสต์นั้น
- แก้ไขโพสต์ → คำนวณเฉพาะ**ส่วนต่าง** (แท็กที่เพิ่มมา +1, ที่ถูกเอาออก −1)
- ยอดถูก**พักรวมในคิว 3 วินาที**แล้วเขียนลงชีตทีเดียว ลดการยิง Google API
- เขียนไม่สำเร็จ → **คืนของกลับเข้าคิว** แล้วลองใหม่แบบถอยห่าง (3 → 6 → 12 → 24 → 48 วินาที) ยอดไม่หาย
- ตอนปิดบอท ยอดที่ยังค้างในคิวจะถูกเขียนลงชีตให้จบก่อน

> บอทจำโพสต์ล่าสุดได้ 2,000 โพสต์ (ราว 14 วันที่ปริมาณปัจจุบัน) เก็บไว้ในหน่วยความจำเท่านั้น — **บอทรีสตาร์ทแล้วหาย** ถ้ายอดเพี้ยนให้ใช้แผงควบคุมนับใหม่

### 👋 ต้อนรับ & ลงทะเบียน (`welcome`)

- สมาชิกเข้าใหม่ → ส่ง embed ต้อนรับพร้อมปุ่มลงทะเบียนในห้อง `WELCOME_CHANNEL_ID`
- กรอกฟอร์ม (ชื่อ IC / เบอร์ IC / อายุ OOC) → บอทหาแถวว่างที่มีรหัสในชีตทะเบียน แล้วเขียนข้อมูลลงไป
- เปลี่ยนชื่อเล่นใน Discord ให้เป็น `รหัส + ชื่อ IC` อัตโนมัติ
- คนที่ถูกตั้งสถานะ `อนุมัติ` ใน Pending Sheet ไว้แล้ว จะข้ามขั้นตอนกรอกฟอร์มได้เลย
- สมาชิกออกจากเซิร์ฟเวอร์ → ส่ง embed อำลา + เขียน `ออกจาก Discord` ลงคอลัมน์ N

### ⏱️ ลงเวลา (`logtime`)

อ่านข้อความ/embed ในห้อง `LOGTIME_CHANNEL_ID` แล้วจับรูปแบบรายงานเข้า-ออกเวรหลายแบบ
(`รายงานตัวเข้าเวรของ - ...`, `ชื่อ - ...` ฯลฯ) จากนั้นบันทึกวัน-เวลา และ**บวกเวลาสะสม**ลงชีตทะเบียน

### 🚔 ส่งต่อรายงานคดี (`bypd` / `proctor`)

เฝ้าดูห้อง `LOGCASE_CHANNEL_ID` และ `LOGTAKE2_CHANNEL_ID` แล้วส่งต่อไปห้องปลายทางตามประเภท:

| เจอคำ | ส่งไปห้อง |
|---|---|
| `BYPD` / `PD ##` | `BYPD_SEND_CHANNEL_ID` |
| `อุ้มห่อ` | `CARRY_SEND_CHANNEL_ID` |
| `TAKE2` | `TAKE2_SEND_CHANNEL_ID` |
| `PROCTOR` | `PROCTOR_SEND_CHANNEL_ID` |

บอทแปลงรหัส 2–3 หลัก (เช่น `BYPD 101 102`) เป็นการแท็กคนจริงโดยค้นจากชีตทะเบียน
มี cache 60 วินาที และ**ส่งทีละรายการ**ผ่าน lock เพื่อไม่ให้ชน rate limit ของ Discord

### 🏷️ แก้แท็ก (`edit-tag`)

คลิกขวาที่ข้อความ → **Apps → Edit Tags** เพื่อแก้ว่าคดีนั้นแท็กใครบ้าง (ยอดในชีตจะปรับตามอัตโนมัติ)
สิทธิ์การใช้งานคุมด้วย `EDIT_TAG_MODE`

### ⚙️ แผงควบคุม (`recount`)

`/recount` วางแผงปุ่มในห้อง — ใช้ตั้งค่าทุกอย่างโดยไม่ต้องเปิด Google Sheet

| ปุ่ม | ทำอะไร |
|---|---|
| เริ่ม/หยุดนับข้อความเก่า | รื้อนับยอดใหม่ทั้งหมดจากประวัติข้อความจริงในห้อง กดซ้ำเพื่อหยุดกลางคัน |
| ตั้งค่า — นับเคส / ต้อนรับ / ระบบคดี / TAKE2 / ชีตลงทะเบียน | เปิด modal แก้ config แล้วเขียนกลับลงชีตให้ |
| รีเฟรช config | โหลด config ใหม่จากชีต |
| ส่งย้อนหลัง BYPD | ไล่ส่งรายงานที่ตกหล่นอีกรอบ |

## โครงสร้างโปรเจกต์

```
src/
├── index.ts              จุดเริ่ม — validate config, watchdog, health server, graceful shutdown
├── config/               อ่านและตรวจค่าจาก .env + ค่าคงที่ของระบบ
├── core/
│   ├── sheet.service.ts  คุยกับ Google Sheets (retry + backoff + throttle + cache)
│   ├── config.service.ts โหลด config จากชีต
│   ├── cache.ts          in-memory cache แบบมี TTL
│   ├── mutex.ts          lock กันเขียนชนกัน
│   ├── lock.service.ts   รายการ lock ทั้งหมดของระบบ

│   ├── credentials.ts    อ่านกุญแจ Google จาก env หรือไฟล์
│   ├── gateway-status.ts สถานะ shard / close code / login error ที่ควรรู้
│   ├── login-attempts.ts ตัวนับเชื่อมต่อไม่สำเร็จ (เก็บลงดิสก์ รอดจากการรีสตาร์ท)
│   └── logger.ts         log ลง stdout + ไฟล์ (หมุนไฟล์เองเมื่อเต็ม 5 MB)
├── features/             แต่ละฟีเจอร์แยกโฟลเดอร์ มี listener.ts เป็นตัวลงทะเบียน event
│   ├── count/  welcome/  logtime/  bypd/  proctor/
│   └── edit-tag/  editpd/  recount/  clear/  reload/
├── services/             ฟังก์ชันที่ใช้ร่วมหลายฟีเจอร์
└── types/                type + ค่าคงที่ที่ใช้ร่วมกัน
```

**การเพิ่มฟีเจอร์ใหม่:** สร้างโฟลเดอร์ใน `src/features/` ที่ export ฟังก์ชัน `setupXxxFeature(client)`
แล้วเพิ่มเข้าไปใน `featureSetups` ที่ [`src/index.ts`](src/index.ts) — ฟีเจอร์ที่โหลดพังจะถูก log ไว้แต่ไม่ทำให้บอทล้ม

> ⚠️ **Lock `locks.count` ใช้ร่วมกันระหว่างนับสดกับนับใหม่โดยตั้งใจ** ห้ามแยกเป็นคนละตัว
> ไม่งั้นการนับใหม่ที่กินเวลาเป็นนาทีจะถูกนับสดเขียนแทรก แล้วโดนเขียนทับด้วยข้อมูลเก่า

## พัฒนา / ทดสอบ

| คำสั่ง | ทำอะไร |
|---|---|
| `npm run dev` | **รันบอทจริง**บนเครื่อง (watch — แก้โค้ดแล้วรีโหลดเอง) |
| `npm run build` | คอมไพล์ TypeScript → `dist/` (รัน lint + typecheck ให้ก่อนอัตโนมัติ) |
| `npm start` | รันจาก `dist/` |
| `npm test` | รันเทสทั้งหมด (vitest) |
| `npm run typecheck` | ตรวจ type อย่างเดียว |
| `npm run lint` | ตรวจ lint อย่างเดียว |
| **`npm run check`** | **ตรวจครบทุกอย่างเหมือน CI — ใช้ก่อน push** |

### `dev` กับ `check` ต่างกันยังไง

`npm run check` **ไม่ได้รันบอท** — ตรวจโค้ดเสร็จก็จบ บอทไม่ได้ออนไลน์

| | `npm run dev` | `npm run check` |
|---|---|---|
| บอทออนไลน์ใน Discord | ✅ | ❌ |
| จับโค้ดพัง / type ผิด / เทสแดง | ❌ | ✅ |
| ดูว่าปุ่มกดแล้วขึ้นอะไร, embed สวยไหม | ✅ | ❌ |

- แก้ของที่**ผู้ใช้เห็น** (ปุ่ม, embed, ข้อความตอบกลับ) → ต้อง `npm run dev` ไปกดทดลองใน Discord จริงก่อน
- แก้ของที่**ไม่กระทบการใช้งาน** (comment, refactor, เพิ่มเทส) → `npm run check` อย่างเดียวพอ

### ⚠️ ห้ามรัน `npm run dev` ตอนบอทบนโฮสต์ยังทำงานอยู่

ทั้งสองตัวใช้ `BOT_TOKEN` เดียวกัน = **บอท 2 ตัวรับ event เดียวกัน** ผลคือ:

| เหตุการณ์ | ความเสียหาย |
|---|---|
| มีคนโพสต์แท็ก | **นับยอดเข้าชีต 2 ครั้ง** — ยอดเบิ้ลทันที |
| มีรายงาน BYPD เข้ามา | ส่งต่อไปห้องปลายทาง **2 ข้อความ** |
| มีคนลงทะเบียน | สองตัวแย่งกันเขียนแถวเดียวกัน |

Mutex ในโค้ดกันการเขียนทับได้แค่**ภายใน process เดียว** ข้าม process กันไม่ได้

**ทางแก้ (เลือกอย่างใดอย่างหนึ่ง):**

1. ปิดบอทบนโฮสต์ก่อนทุกครั้ง (suspend service) แล้วค่อยเปิดกลับหลังทดสอบเสร็จ
2. **แนะนำ** — สร้าง Discord bot อีกตัวไว้เทสโดยเฉพาะ ใช้ `.env` คนละไฟล์ ชี้ไปเซิร์ฟเวอร์ทดสอบและชีตทดสอบ จะได้ไม่ต้องปิด ๆ เปิด ๆ และไม่มีทางไปแตะข้อมูลจริง

รัน **test → lint → typecheck → build** ครบเท่ากับที่ CI ตรวจ ถ้าเขียวหมดแปลว่า CI จะเขียวด้วย

> ⚠️ `npm test` อย่างเดียว **ไม่พอ** — มันตรวจแค่เทส ถ้าลืมลบตัวแปรที่ไม่ได้ใช้ (lint ไม่ผ่าน) หรือ type ไม่ตรง (typecheck ไม่ผ่าน) เทสก็ยังเขียวอยู่ แต่ CI จะแดง

ลำดับที่ควรทำ:

```
1. เขียนโค้ด

6. git push
7. CI รันซ้ำบน GitHub (1–2 นาที)
8. โฮสต์ deploy
```

ข้อ 2–3 ข้ามได้ถ้าแก้แค่ของที่ไม่กระทบการใช้งาน

**CI** ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) รันทุก push และ pull request ตามลำดับ:
`npm ci` → lint → typecheck → test → build

## Deploy

โปรเจกต์ยังไม่มีไฟล์ deploy สำเร็จรูป (Dockerfile / Procfile) ต้องตั้งค่าบนโฮสต์เอง:

| ช่อง | ค่า |
|---|---|
| Build command | `npm ci && npm run build` |
| Start command | `npm start` |
| Node version | 22 ขึ้นไป |

**ตั้งค่าที่แนะนำบนโฮสต์:**

- ใส่ `GOOGLE_JSON_KEY` เป็น environment variable แทนการอัปโหลด `credentials.json`
- ตั้ง `LOG_TO_FILE=false` แล้วให้แพลตฟอร์มเก็บ log จาก stdout
- ตั้ง `RENDER_EXTERNAL_URL` เป็น URL จริงของบอท เพื่อให้ self-ping กันโฮสต์ฟรีหลับทำงาน
- ชี้ health check ของแพลตฟอร์มไปที่ `/health`

### ⚠️ CI แดงไม่ได้หยุด deploy

โฮสต์อย่าง Render / Railway ตั้งค่าเริ่มต้นคือ **เห็น push ปุ๊บ deploy ทันที** ไม่รอดูผล GitHub Actions
ทั้งสองอย่างวิ่งคู่กันโดยไม่เกี่ยวข้องกัน:

```
git push ─┬─→ โฮสต์เริ่ม deploy ทันที
          └─→ CI รัน แล้วขึ้นแดง 2 นาทีถัดมา

ผลลัพธ์: บอทพังอยู่บนโฮสต์แล้ว แต่ GitHub เพิ่งจะบอกว่ามีปัญหา
```

ยิ่ง commit ลง `main` ตรง ๆ = ทุก push ขึ้น production ทันที
**ด่านจริงจึงอยู่ที่ `npm run check` บนเครื่องก่อน push** — CI เป็นแค่ตาข่ายสำรองกันลืม

ถ้าต้องการให้ CI บล็อกได้จริง ต้องตั้ง **branch protection** บน GitHub (บังคับให้ CI ผ่านก่อนจึง merge ได้)
แล้วเปลี่ยนไปทำงานผ่าน Pull Request แทนการ push เข้า `main` ตรง ๆ

## ดูแลระบบ

### Health check

```
GET /health
```

```json
{
  "status": "ok",
  "discord": true,
  "inGuild": true,
  "lockedOut": false,
  "loginAttempts": 0,
  "lockOutReason": null,
  "guilds": 1,
  "shards": [{ "id": 0, "status": "Ready", "ping": 42 }],
  "wsPing": 42,
  "uptime": 3600,
  "timestamp": 1700000000000
}
```

| field | ความหมาย |
|---|---|
| `discord` | shard ทุกตัวพร้อมรับ event จริง — ไม่ใช่ `client.isReady()` ที่ค้าง `true` ไว้ |
| `inGuild` | ยังอยู่ในเซิร์ฟเวอร์หลัก (`GUILD_ID`) หรือไม่ — ถูกเตะ/แบนแล้วจะเป็น `false` |
| `lockedOut` | บอทหยุดพยายามเชื่อมต่อเองแล้ว (เชื่อมไม่สำเร็จครบเพดาน — ดูหัวข้อถัดไป) |
| `loginAttempts` | เชื่อมต่อไม่สำเร็จไปแล้วกี่ครั้ง (นับข้ามการรีสตาร์ท) |
| `lockOutReason` | เหตุผลที่หยุด — `null` เมื่อยังไม่ได้หยุด |
| `guilds` | จำนวนเซิร์ฟเวอร์ที่บอทเห็นตอนนี้ |
| `shards` | สถานะ shard ทีละตัว (`Ready`, `Reconnecting`, …) พร้อม ping |

ตอบ **200** เมื่อ `discord` และ `inGuild` เป็นจริงทั้งคู่ — นอกนั้นตอบ **503**
โดย `status` จะบอกสาเหตุว่า `login_locked_out`, `discord_disconnected` หรือ `not_in_guild`
ตั้ง UptimeRobot หรือ monitor ตัวอื่นชี้มาที่นี่ได้เลย
(`GET /` ตอบ `Bot is alive! ✅` เฉย ๆ ไม่ได้เช็คสถานะ Discord)

### Watchdog

เฝ้าดู**การเชื่อมต่อ Discord** จากสถานะ shard — ไม่ใช่ HTTP request ของตัวเอง
และไม่ใช้ `client.isReady()` เพราะค่านั้นค้าง `true` ตั้งแต่ต่อติดครั้งแรก discord.js ไม่เคยตั้งกลับ
ต่อให้ shard หลุดไปแล้วก็ตาม

Discord หลุดเกิน **15 นาที** จะสั่งรีสตาร์ทอัตโนมัติ จำกัดไม่เกิน **8 ครั้ง / 24 ชั่วโมง**
เพื่อไม่ให้วนรีสตาร์ทไม่จบ (ถึงขีดจำกัดแล้วจะเตือนใน log ชั่วโมงละครั้ง ไม่สแปมทุก 15 นาที)

นอกจาก watchdog ยังมีตัวบอกสาเหตุใน log/ชีตอีก 3 จุด เพื่อไม่ให้เหตุการณ์สำคัญหายเงียบ:

| เหตุการณ์ | สิ่งที่บันทึก |
|---|---|
| หลุดชั่วคราว / เน็ตสะดุด (`shardReconnecting`) | `WARN` “Shard N กำลังเชื่อมต่อใหม่” — discord.js ต่อให้เอง ไม่ต้องยุ่ง |
| กลับมาจริง (`shardReady` / `shardResume`) | `INFO` — resume ไม่ได้จะ re-identify ใหม่และไม่มี `shardResume` ตามมา จึงต้องดู `shardReady` ด้วย |
| หลุดด้วย code ที่ต่อใหม่ไม่ได้ (`shardDisconnect`: 4004, 4010–4014) | `ERROR` + สั่งรีสตาร์ท เพราะต่ออีกกี่ครั้งก็ไม่ติด (ต้องแก้ token/intents) |
| ถูกนำออกจากเซิร์ฟเวอร์ (`guildDelete`) | `ERROR` พร้อมชื่อเซิร์ฟเวอร์ — เตะกับแบนแยกจากฝั่ง gateway ไม่ได้ |
| `client.login()` ค้าง (Discord ไม่ตอบ handshake) | `ERROR` เมื่อครบ 60 วิ แล้วเข้าสู่เพดานในหัวข้อถัดไป — เดิมค้างเงียบได้เป็นชั่วโมงโดยไม่มี log เลย |

### หยุดเองเมื่อเชื่อมต่อไม่ได้ (กันการยิง Discord)

ตอนบูตบอทจะถาม Discord 1 ครั้งที่ `GET /api/v10/gateway/bot` — endpoint เดียวกับที่ `client.login()` ใช้
แนบ `Authorization` และ `User-Agent` แบบเดียวกับ discord.js เพื่อให้เห็นเงื่อนไขจริงเป๊ะ ๆ

- ผ่าน (200) → log `Discord API ตอบปกติ (HTTP 200 · 120 ms)` แล้วต่อด้วย `client.login()`
- ไม่ผ่าน → log `HTTP <status>` + `Retry-After` + header ที่เกี่ยวข้อง (`x-ratelimit-*`, `cf-ray`, `server`, `via`)
  + body ของ Discord **และไม่เรียก `client.login()` เลย** เพราะ `@discordjs/rest` แปล 429 เป็น
  "รอแล้วลองใหม่ไม่จำกัดจำนวนครั้ง" (ไม่ throw) — ปล่อยให้ login ทำงานต่อคือการยิง Discord ถี่ขึ้นเรื่อย ๆ
  จน `login()` ค้างเงียบเป็นชั่วโมง และหน้าต่างลิมิตยิ่งยาวขึ้น

ถ้าเชื่อมต่อไม่สำเร็จ**ครบ 2 ครั้งติดกัน** (นับข้ามการรีสตาร์ท เพราะเก็บใน `logs/login-attempts.json`)
บอทจะหยุดส่งคำขอไป Discord ทั้งหมด แต่ยังรัน HTTP ไว้ให้ `/health` ตอบ `login_locked_out`
พร้อม `lockOutReason` — watchdog ก็จะไม่สั่งรีสตาร์ทในโหมดนี้ (การรีสตาร์ท = ยิง Discord ใหม่)

| สถานการณ์ | สิ่งที่เกิดขึ้น |
|---|---|
| ล้มเหลวครั้งที่ 1 | log `WARN` แล้วออกไปให้โฮสต์สตาร์ทใหม่หนึ่งรอบ (มีแค่รอบเดียว) |
| ล้มเหลวครั้งที่ 2 | หยุดเลย ไม่ exit — `/health` เป็น 503 `login_locked_out` |
| บูตมาพร้อมตัวนับครบ 2 | ไม่ยิงคำขอไป Discord แม้แต่ครั้งเดียว |
| token/intents ผิด (401/403/4004/4013/4014) | หยุดทันที ไม่ลองซ้ำ เพราะลองอีกกี่ครั้งก็ได้ผลเดิม |
| เขียนไฟล์ตัวนับไม่ได้ (ดิสก์อ่านอย่างเดียว) | หยุดทันทีเช่นกัน ไม่งั้นรีสตาร์ทแล้วนับใหม่จาก 0 จะวนไม่จบ |
| ต่อติดสำเร็จ | ลบไฟล์ตัวนับทิ้งเอง |

**วิธีปลดล็อก** (หลังแก้ต้นเหตุแล้ว): deploy ใหม่ (ได้ดิสก์ใหม่) หรือลบ `logs/login-attempts.json`
แล้วสั่ง restart service — บอทจะกลับมาลอง 2 ครั้งเหมือนเดิม

### Log

เก็บ 3 ที่ แยกตามอายุการใช้งาน:

| ที่เก็บ | เก็บอะไร | ย้อนหลัง |
|---|---|---|
| stdout | ทุกบรรทัด (มีสีตามระดับ) | ตามที่แพลตฟอร์มเก็บให้ |
| ไฟล์ `logs/app.log` | ทุกบรรทัด ถ้า `LOG_TO_FILE=true` | 2 ไฟล์สลับกัน ละไม่เกิน 5 MB |
| หน่วยความจำ | ทุกบรรทัด | **24 ชั่วโมง** (เพดาน 20,000 บรรทัด) |
| ชีตแท็บ `Log-Debug-Bot` | **เฉพาะที่สำคัญ** | **100 แถวล่าสุด** (ตัดส่วนเกินทุกชั่วโมง) |

- เขียนไฟล์พังเมื่อไหร่ บอทจะเลิกเขียนไฟล์แล้วไปต่อ ไม่ล้มทั้งระบบ
- **ความลับถูกกรองออกตอนเก็บ** (กุญแจ Google, โทเคน Discord, `token=`, `Authorization: Bearer`) — กรองที่ทางเข้า ไม่ใช่ตอนแสดงผล
- แท็บ `Log-Debug-Bot` อยู่ไฟล์ **Settings** เดียวกับ `config` (ฝั่งเว็บใช้แท็บ `Log-Debug-web` ในไฟล์เดียวกัน)
- บอทตัด **ทั้งสองแท็บ** ให้เหลือ 100 แถวล่าสุดทุกชั่วโมง เพราะเว็บรันบน Vercel ซึ่งไม่มีตัวตั้งเวลาของตัวเอง

**อะไรที่ลงชีต:** ทุก `ERROR` / `WARN` + เหตุการณ์ระดับ `INFO` ที่ต้องย้อนดูได้ (ลงทะเบียน, คนเข้า-ออกเซิร์ฟ, ใครกดรีโหลด, สรุปการนับรายชั่วโมง, Discord หลุด/ต่อใหม่)

**อะไรที่ไม่ลงชีต:** `DEBUG` ทั้งหมด และ `INFO` ของ `BYPD` (มีหนึ่งบรรทัดต่อหนึ่งคดี ~2,160 แถว/วัน ชีตจะอืดภายในเดือนเดียว) — ดูจากหน่วยความจำ 24 ชม. ผ่าน `GET /logs` แทน

รวบส่งลงชีตนาทีละครั้ง ไม่เขียนทีละบรรทัด เพราะบอทกับเว็บใช้บัญชี Google ตัวเดียวกัน
โควต้าเขียนจึงแชร์กัน — ถ้า log แย่งโควต้าไป การเขียนยอดนับจะเริ่มพลาด

### ขอ log ย้อนหลัง

```
GET /logs
```

ต้องมีรหัสผ่านตรงกับ `LOG_API_TOKEN` ส่งมาทาง header `x-log-token` (แนะนำ) หรือ `?token=`
**ไม่ตั้ง `LOG_API_TOKEN` = ช่องนี้ปิด** (ตอบ 503)

| ตัวกรอง | ความหมาย |
|---|---|
| `?level=ERROR,WARN` | เอาเฉพาะระดับเหล่านี้ |
| `?context=นับเคส` | เอาเฉพาะหมวดนี้ |
| `?q=คำค้น` | มีคำนี้ในข้อความหรือหมวด |
| `?since=1700000000000` | เอาเฉพาะที่ใหม่กว่าเวลานี้ |
| `?limit=500` | เอาท้ายสุดกี่บรรทัด (เพดาน 2,000) |

ตอบกลับมีสถานะบอท (`ready`, `uptime`, `wsPing`), ช่วงเวลาที่หน่วยความจำครอบคลุม,
จำนวนแถวที่ยังไม่ได้เขียนลงชีต, จำนวนยอดนับที่ยังค้างในคิว และรายการ log

### Graceful shutdown

ได้รับ `SIGINT` / `SIGTERM` แล้วบอทจะ:

1. เคลียร์ timeout ที่ค้าง
2. **เขียนยอดที่ยังค้างในคิวลงชีตให้จบ** (รอไม่เกิน 5 วินาที)
3. ปิดการเชื่อมต่อ Discord และ HTTP server
4. flush log แล้วออก

## แก้ปัญหาที่เจอบ่อย

| อาการ | สาเหตุ / วิธีแก้ |
|---|---|
| บอทไม่ยอมสตาร์ท ขึ้น `❌ การตรวจสอบ Config ล้มเหลว` | อ่านรายการที่ขึ้นมา — บอกครบทุกจุดที่ผิดในรอบเดียว |
| `ไม่พบกุญแจ Google` | ยังไม่ได้ใส่ `GOOGLE_JSON_KEY` และไม่มีไฟล์ `credentials.json` ที่ root |
| Google ปฏิเสธกุญแจโดยไม่บอกสาเหตุ | ตรวจว่า service account ถูกแชร์ชีตเป็น **Editor** แล้วหรือยัง และเปิด Google Sheets API แล้วหรือยัง |
| ยอดในชีตไม่ขยับ | `configService` โหลดไม่สำเร็จ (ดู log `CONFIG`) หรือ ID ห้องใน `COUNT_CHANNEL_IDS` ไม่ตรง — ลอง `/reload` |
| แก้แท็กแล้วยอดไม่เปลี่ยน | โพสต์นั้นเก่ากว่า 2,000 โพสต์ล่าสุด หรือบอทเพิ่งรีสตาร์ท (ความจำอยู่ใน memory) — ใช้แผงควบคุมนับใหม่ |
| คำสั่ง slash ไม่ขึ้น | Global command ใช้เวลาถึง 1 ชั่วโมงหลัง deploy ครั้งแรก |
| บอทอ่านข้อความไม่เห็น | ยังไม่ได้เปิด **Message Content Intent** ใน Developer Portal |
| ดึงรายชื่อสมาชิกไม่ได้ | ยังไม่ได้เปิด **Server Members Intent** |
| ปุ่มแผงควบคุมค้างที่ "หยุดทำงาน" | แผงค้างจากรอบก่อนที่บอทรีสตาร์ทกลางคัน — กดปุ่มหนึ่งครั้งเพื่อรีเฟรชแผงให้ตรงความจริง |
| `/health` ตอบ `login_locked_out` | บอทเชื่อมต่อไม่สำเร็จครบ 2 ครั้งแล้วจึงหยุดเอง (กันการยิง Discord) — แก้ `lockOutReason` ใน `/health` หรือ log `STARTUP` ก่อน แล้ว deploy/ลบ `logs/login-attempts.json` เพื่อปลดล็อก |
| log ขึ้น `HTTP 429` ตอนบูต | Discord/Cloudflare จำกัด IP ขาออกของโฮสต์ (IP ร่วมกับ service อื่น) — ดู `Retry-After` กับ `cf-ray` ที่ log ไว้ ถ้าเป็นลิมิตที่ระดับ IP ให้ย้าย region หรือย้ายไปโฮสต์ที่มี IPv4 ของตัวเอง |
